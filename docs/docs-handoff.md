# Application and documentation coordination

Maintain reader guides, migration instructions, and API references in [apps/docs](../apps/docs/README.md). VitePress and the application share the workspace lockfile and load interactive examples from the same workspace. Previous site content and history remain in [ray-template-doc](https://github.com/XiaoDaiGua-Ray/ray-template-doc).

The site targets v6. Source links use monorepo paths, and release builds use `RAY_TEMPLATE_SOURCE_REF` to pin links to the release commit. Inline examples build against workspace source. See the [version boundary](../apps/docs/migration.md) for v5 source and release tags.

## Update workflow

1. When application changes affect public imports, configuration, caching, or behavior, update the module notes and affected `apps/docs` pages/examples in the same change. Add breaking changes to the migration guide.
2. Display source from the running example. Lightweight examples live in `apps/docs/examples` and use public shared-package entry points. Examples needing application context embed `example.html`, with source references pointing to the actual admin demo page. Use the [documentation topic index](../harness/context/docs.md) to locate them.
3. Run relevant tests or scope checks for application changes. For documentation structure, links, code examples, or theme changes, run `pnpm harness verify docs`. Wording-only corrections need source and formatting checks. Reuse a completed check that includes `docs:check` if its relevant files have not changed since.
4. Select browser coverage using the [Harness impact dimensions](../harness/README.md#browser-verification). View the changed page when rendering structure or layout is at risk; exercise only the affected interactive example. Add navigation, search, legacy paths, themes, and narrow widths only when each is affected. For site themes, global navigation, or release acceptance, select representative pages for shared behavior. Maintainer documentation and wording-only reader-documentation corrections do not trigger browser checks.
5. Use `pnpm docs:preview` for documentation pages and lightweight examples. For changes to embedded admin examples, deployment bases, or combined output, use `pnpm pages:build` and the combined preview. Verify old and new live URLs separately for a site migration.
